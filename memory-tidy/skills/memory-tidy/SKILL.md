# auto memory 整理 playbook

プロジェクトの auto memory を、情報を失わずに軽く・引きやすく保つための整理手順。

MEMORY.md は**毎セッション自動ロードされるハブ**。肥大すると毎回コンテキストを食い、肝心の進行中タスクが埋もれる。さらに memory ファイルは**コンテキスト圧縮（compaction）の境界を越えて生き残る唯一の場所**——会話中の経緯は圧縮で失われるが、memory に書いた事実は残り、次セッションの開始時にそこから状態を復元できる。だから整理の目的は「自動ロードされる MEMORY.md を要点だけに保ち、詳細は辿れる場所（task-*.md / ナレッジファイル / git / PR）へ逃がす」こと。**削除ではなく配置の最適化**と捉える。

## 大原則

- **プロジェクトの運用ルールが最優先**。MEMORY.md 冒頭の「メモリ運用ルール」（行数上限・ファイル命名規約・ライフサイクル）を最初に読み、本 skill の汎用手順より優先する。両者が食い違ったらプロジェクト側に従う。
- **情報を捨てない。配置を変える**。MEMORY.md から消す内容は、必ず別の辿れる場所（task-*.md / ナレッジファイル / 完了記録 / git・PR 履歴）へ移してから消す。要約に置き換えるときも、詳細へのリンクを残す。
- **圧縮の判断軸（Golden rule）**: 各行について「これを消したら、次に読む自分や別セッションの Claude が判断を誤るか？」を問う。**誤らないなら消す**。残すのは durable（長く効く）かつ non-obvious（コードや git から自明でない）知識——環境固有のエラーと回避策・必須コマンドフラグ・暗黙の依存・アーキの癖・要注意ファイル。逆に、自明な説明・一過性の経緯・コミット列挙のような git/PR で足りる情報は落とす。
- **削除・圧縮は破壊的**。範囲をユーザーに確認してから実行する（後述 §2）。判断に迷うエントリは消さず残し、ユーザーに挙げる。
- **書いた知見が「届く」かまで設計する（到達性）**。memory への到達経路は3つ —— ①**MEMORY.md の自動ロード**（唯一確実だが容量上限がある枠）②**recall**（frontmatter の `description` が関連性判定に使われる自動想起。発火はこちらから制御・観測できない）③**手動 Read**（読むかはモデル任せで保証がない）。**こちらで制御できるのは①と、①から名指しで Read を命じる手続きだけ**。だから整理では、ファイルごとにどの経路で届くかを決める:
  - **トリガーを事前特定できない**（どのセッションでも効きうる＝作業ルール・進行中状態・ルーティング）→ ①の常駐枠へ
  - **特定できる**（特定の作業種別・症状・エラー・PR番号で発火）→ ②③向けに置き、**`description` をトリガー語で書く**（症状・コマンド名・エラーメッセージ断片を先頭に。結論だけの要約はセッション中の文脈と一致せず想起されない）
  - **frontmatter が無いファイルは②の応募資格すら無い**。知見ファイルには必ず `name` / `description` / `metadata.type` を付ける
  - 「自動ロードされない索引を読め」と書くだけでは②③に賭けたまま。**最頻の消費場面（実機検証・レビュー・デバッグ）は、自動ロードされる資産（CLAUDE.md / rules / スキル）から名指しで Read を命じて手続き化する**

## 進め方（チェックリスト）

コピーして進捗を追う:

```
- [ ] 1. 現状把握（行数/容量・全文通読・運用ルール確認）
- [ ] 2. 整理範囲をユーザーに確認
- [ ] 3. 完了タスクの処理（削除→完了記録→知見昇格→残作業の温存）
- [ ] 4. 肥大エントリを task へ退避し要約化
- [ ] 5. CLAUDE.md へ昇格すべき普遍ルールの拾い上げ（任意）
- [ ] 6. ゴミ掃除（空ファイル/壊れリンク/重複/小ファイル乱立）
- [ ] 7. 検証（行数・容量・リンク整合）→ 報告
```

## 1. 現状把握

対象は**現在のプロジェクトの auto memory ディレクトリ**（システムが MEMORY.md を自動ロードしているパス。通常 `~/.claude/projects/<project>/memory/`）。そのディレクトリで:

- まず同梱の health check を実行する: `bash <本skillのベースディレクトリ>/scripts/check_health.sh <memoryディレクトリ> --check-prs`。サイズ一覧・**読込上限の超過警告と末尾セクション**（縮退順序の確認）・空ファイル・壊れリンク（相対リンク/wiki リンク両方）・**frontmatter / description 欠落**（recall の応募資格が無い知見ファイル）・**被参照ゼロの孤児**・PR 番号の gh 実状態照合が一括で出る（読み取り専用）。上限値は `MEMORY_BYTE_LIMIT` 環境変数で上書きする（既定 24985 = 24.4KB）。gh 照合はプロジェクトリポジトリ内から実行すること。以下の手動確認はスクリプトの出力を読むための背景知識、およびスクリプトが使えない環境向け。
- **スクリプトの gh 照合は補助に過ぎない**。進行中エントリのチケットキーを集め、**課題トラッカーのステータスを一括照会する**（§3 の完了判定を参照）。プロジェクト側にトラッカー照会の手段（スキル・CLI）があればそれを使う。
- `ls -la` ＋ `wc -l *.md` で全ファイルの行数を一覧。MEMORY.md の行数・バイト数を確認し、運用ルールの上限（例: 200 行）と比較する。**行数だけでなくバイト数（読込上限）も実効上限として扱う**——MEMORY.md は行数上限内でもバイト超過で末尾セクションが自動ロード時にドロップする（フックが容量警告を出すならそれが実効上限）。**行削減とバイト削減は別手段**: 索引は1ファイル1行で行数が構造的下限になるため、バイトは「説明文の短縮」、行数は「エントリ統合／別ファイル化」で攻める。
- MEMORY.md を**通読**する。特に「進行中タスク」「索引」「完了記録」の各セクション構造を把握する。自動ロードで冒頭しか読めていない場合も、整理時は全文を読む（大きくて一度に読めなければ offset 分割、または Grep で目的セクションを特定して読む）。
- 冒頭の運用ルールを読み、命名規約（ハブ / ナレッジファイル `{topic}.md` / `task-{name}.md`）とライフサイクルを確認する。
- **構造の健全性を確認**する。MEMORY.md が途中で切れている・見出しが重複している・文字化け（mojibake）しているなど壊れている兆候があれば、整理せずユーザーに報告する（壊れた入力を整理すると破損が固定化する）。
- **整理前にスナップショットを取る**。memory ディレクトリが git 管理下なら作業前状態を commit/stash で固定し、そうでなければ scratchpad（または `$TMPDIR`）へ `cp MEMORY.md <scratchpad>/MEMORY.md.bak` する。破壊的編集の巻き戻し手段を確保しておく。**bak を memory ディレクトリ内に作らない**——sandbox の unlink 制限で作業後に消せないことがあり、残った .bak は次セッション以降の recall・grep のノイズになる。
- **memory ディレクトリは Bash から書けないことがある**（sandbox の filesystem 制限。`mv` / `cp` / `touch` が `Operation not permitted`）。**この制限は `!` によるユーザー実行にも及ぶ**——同じセッション内のシェルなので回避にならない。編集は Write/Edit ツールで行い、**ファイルの移動・削除は「Claude Code の外のターミナルで実行してください」とユーザーに依頼する**。依頼するコマンドは**スクリプト化して1行で渡す**（長いコマンドは入力欄の折り返しで改行が入り壊れる）。
- 運用ルールに**行数上限の記載が無い**プロジェクトでは、圧縮目標値をユーザーに確認する。確認が取れるまでは、完了タスク除去・壊れリンク掃除など非破壊で低リスクな項目に留める。

肥大の主因はたいてい次のどれか。狙いを定める:
- **完了済みなのに進行中タスクに残っている**エントリ（最優先で除去）
- **実装完了だが PR/レビュー中**の、詳細を抱えた肥大エントリ（task へ退避して要約化）
- 索引の**壊れリンク**（実ファイルが無い）・**重複**・**空ファイル**・**小ファイルの乱立**

## 2. 整理範囲をユーザーに確認

削除・圧縮を伴うので、着手前に範囲を確認する。現状把握で見つけた肥大箇所（どのエントリが何 KB か）を具体的に示してから、おおむね次の3択を提示する:

- **標準（推奨）**: 完了タスクを削除＆完了記録化＋知見をナレッジへ。実装完了で肥大したエントリを task-*.md へ退避し要約化。索引の重複・壊れリンクも整理。
- **軽め**: 明確に完了したタスクの削除のみ。進行中の肥大エントリは触らない。
- **全面再編**: 進行中タスク・索引・feedback 索引・完了記録まで含めて全体を見直し再構成。

## 3. 完了タスクの処理

進行中タスクのうち「✅完了」「マージ済」など明確に終わったものを処理する。**大原則「先にコピー、後で削除」に従い、知見の救出・記録を先に済ませてから最後に削除する**:

> ⚠️ **完了判定は MEMORY.md の表記を信じず、実状態で照合する**。「OPEN」「Draft」「Ready」「マージ待ち」等の表記は前回更新時点のもので陳腐化している前提で扱う。
>
> **一次情報は課題トラッカー（Jira / Linear / GitHub Issues 等）のステータス**。エントリにチケットキーがあれば、**進行中エントリのキーを全部集めて一括照会**する（Jira なら `search --jql 'key in (...)' --fields summary,status`）。**PR 照合だけで完了判定しない**——PR を作らず終わるチケット（spike・調査・ドキュメント・スキル整備）、複数 PR に分かれたチケット、そして**メモリに PR 番号すら書かれていないままマージされたチケット**は、`gh` では原理的に検出できない。実例: 「実装未着手」と書かれたエントリが実は 10 日前にマージ済み（メモリに PR 番号の記載が無く gh 照合をすり抜けた）。
>
> トラッカーのステータスは「完了」以外も見る——**アーカイブ / クローズ / 却下**は監視バックログから落とす対象。逆に**トラッカーが「未着手」でもローカルに実装がある**ことがある（PR 未作成）。その場合はトラッカーでなく実作業の残りで判断し、不整合をエントリに一言残す。
>
> チケットキーが無いエントリ（個人スキル整備など）は、PR 番号があれば `gh pr view <PR#> --json state,mergedAt -q .state`（複数なら for ループで一括）、無ければ `git log` で**実マージ状態を照合**する。**特に `git pull` 直後**は、表記が「進行中」でも実はマージ済みのことが多い。表記だけ見て完了処理から漏らさない。また、進行中エントリは追記更新の繰り返しで**メタ情報の二重貼り付けや陳腐化した残作業表記**（例:「残=PR作成」だが実際は PR Ready 済）が湧く——照合のついでに、残す進行中エントリ内の重複句・古い「残=」表記も実状態と突合して直す。**時間ベースの発火基準**: エントリの日付スタンプが **2週間以上前**の進行中エントリは、表記がアクティブでも必ず実状態を再照合し、動きがなければ塩漬けクラスタへ降格するか完了処理する（プロジェクト運用ルールに別の窓があればそちら優先）。時間はレビューの発火基準であって削除基準ではない——古くてもアクティブなら残す。

1. **再利用知見をナレッジファイルへ救出**する。そのタスクで得た知見（設計の肝・確定方針・ハマりどころ）を集約し、MEMORY.md の索引に 1 行追加する。Golden rule で選別し、durable・non-obvious なものだけ抜き出す（実装ログそのものは git/PR に残るので持ち込まない）。**新ファイルを作る前に既存ナレッジファイルへの追記で済まないか確認する**——小さなファイルが大量に増えると（memory sprawl）かえって引きにくくなる。新領域のときだけ新ファイルを作る。**既存知見の陳腐化も直す**——完了タスクで恒久対応が入った場合、関連する既存ナレッジファイルの「回避策／暫定対処」記述は古くなる。該当ファイルを「恒久対応済（PR#）」へ**実コードで裏取りして更新**する（新規救出だけでなく既存知見のメンテも完了処理の一部）。
2. **完了記録を残す**。プロジェクトに完了記録の置き場（例: 「完了済み PR」テーブル）があれば、そこに 1 行だけ残す（PR 番号・一文サマリ・関連ナレッジへのリンク）。置き場が無ければ、ユーザーに完了記録セクションの新設を提案するか、知見をナレッジへ昇格し PR 番号をナレッジ側に併記して代替する。**保持の基準は時間窓より状態**——「マージ待ち」「人間の残アクション」「引き継ぎの実機確認」のような**未クローズの尾がある行だけを本文で持ち、完全にクローズした行は1行サマリへ落とす**。常駐枠で効いた実績はほぼ全て「尾がある行」由来で、クローズ済みの学びはナレッジへ昇格済みのはずだから常駐させる理由がない。
3. **残フォローアップを取りこぼさない**。完了タスクでも「別 Issue 化待ち」「PdM 議論後に起票」「別 PR で対応予定」などの未完の尾が付いていることがある。これらは消さず、完了記録の行に併記するか、独立した進行中タスク/Issue として残す。完了マーカー（✅）だけ見て丸ごと消すと宿題が消える。
4. ここまで終えてから、**進行中タスクセクションから削除**する。対応する `task-{name}.md` の扱いは**プロジェクトの運用ルールに従う**——「完了後は削除」の運用なら知見救出済みを確認してから削除、「完了済み task-*.md は参照用に保持」の運用なら削除せず進行中からのリンクを外すだけにする（完了記録の行から task へリンクを張り直すのは可）。運用ルール内で記述が食い違う（冒頭ルールは削除・別セクションの注記は保持、など）場合や迷う場合は、削除は不可逆なので**保持に倒して**ユーザーに挙げる。保持運用でも、**完了後 1 ヶ月を超えた task-*.md は memory 直下から `archive/` サブディレクトリへ移動**してよい（自動ロードには影響しないので効果は直下の見通し改善。参照リンクは `./archive/...` へ張り直す）。sandbox の unlink 制限で `mv` が失敗する場合は、archive/ へコピーしたうえで元ファイルの削除をユーザーに依頼する（`! rm <path>`）。

## 4. 肥大エントリの task ファイルへの退避

「実装完了したが PR/レビュー継続中」のような、まだ進行中だが詳細が膨れたエントリは、詳細を `task-{name}.md`（または PRODUCT-XXXX 等のキー付き）へ移し、MEMORY.md 側は**2〜3 行の要約＋ task へのリンク**に圧縮する。

要約に残すべき最小限（Golden rule で取捨）:
- 状態（実装完了 / レビュー中 / ⏸残作業）と担当・ブランチ・PR 番号
- 採用方針の一言と、その**核心的理由**（なぜその設計にしたか）
- デプロイ対象など、ひと目で要る運用情報
- `詳細=[task-...](./task-...md)` リンク

圧縮のイメージ（肥大エントリ → 要約）:
```
- **PRODUCT-XXXX 機能名**（実装完了・PR #NNNN・⏸残=レビュー対応）: 〈方針一言〉採用（〈核心的理由〉）。
  検証=tsc/lint/test 緑。Deploy Target=〈関数名〉+frontend。詳細=[task-PRODUCT-XXXX-....md](./task-PRODUCT-XXXX-....md)
```

詳細（フェーズ別実装・検証ログ・コミットハッシュ・ハマり所）は task ファイル側へ。task ファイルは索引には載せず、MEMORY.md の該当エントリから直接リンクで辿る運用が一般的（運用ルールに従う）。

手順は**先にコピー、後で圧縮**の順を厳守する: ①task ファイルを Write で新規作成し詳細を全部移す → ②それから MEMORY.md の該当ブロックを Edit で要約＋リンクに置換する。逆順（先に MEMORY を削ってから task を書く）にすると、移し忘れた情報が失われる。

### 索引・進行中が肥大したとき（別ファイル化 / クラスタ統合）

行数を削るには、エントリ要約（バイトは減るが行数は減らない）だけでなく**行の統合・分離**が要る:

- **索引の別ファイル化**: ナレッジ索引が数十行に膨れたら、別ファイル（例 `KNOWLEDGE.md`）へ分離し MEMORY.md はポインタ＋カテゴリ一覧だけ残す。**recall トレードオフに注意**——MEMORY.md だけが自動ロードされる構成では、別ファイルは「必要時に Read」運用になり毎回は recall されない。だから**常時効くべきもの（feedback＝作業ルール）は MEMORY.md か CLAUDE.md に残し、必要時参照でよい技術知見だけ分離**する。運用ルール変更を伴うので**ユーザー確認必須＋MEMORY.md 冒頭の運用ルールも整合更新**する（分離先の存在・参照タイミングを明記）。
- **backlog/塩漬けのクラスタ統合**: 進行中タスクに溜まる「未着手 Backlog」「起票済み未着手の計画」が多数あれば、1 項目 1 行でなく「監視・バックログ」「計画・参照」のような **1 行クラスタに束ねる**（チケットリンクは保持）。アクティブ（実装中/レビュー中）と塩漬け（未着手）を分けると進行中セクションが一気に軽くなる。
- **縮退順序を設計する（セクション順＝生存優先順）**: 自動ロードは上限超過で**末尾からドロップ**する。つまりセクションの並びがそのまま生存優先順になっている。**消えても判断が壊れないもの（完了記録・過去ログ）を最下段へ、消えると困るもの（運用ルール・進行中タスク・作業ルール・ユーザー設定）を上へ**並べ替える。実例: 末尾が「重要パス」「ユーザー設定」のままだと、超過した瞬間に最も要るものから静かに失われる。落ちる位置に置いたセクションには「ここが落ちても判断は壊れない」理由を一行添えておく（次に読む人が並びの意図を壊さないため）。ドロップが先頭からの実装なら逆になるので、プロジェクトの運用ルールに書かれた挙動に従う
- **完了記録の水平線繰り上げ**: 完了記録（完了済み PR テーブル等）は「直近のみ」に保ち、古い行は「〜YYYY-MM-DD 以前は git/GitHub 履歴・ナレッジ索引参照」の脚注 1 行へ集約する。保持窓はプロジェクト運用ルールの定義に従い、無ければ**直近 2 スプリント相当（目安 2 週間）**をデフォルトにする。バイト削減の効きが大きい定番手段。落とす行が知見リンク（`[[...]]`）や task リンクを含む場合、その知見がナレッジ索引から辿れること・task ファイルが残ることを確認してから落とす（詳細が Jira コメントや PR 本文に記録済みの行は、そのポインタさえあれば安心して短縮できる）。

## 5. CLAUDE.md へ昇格すべき普遍ルールの拾い上げ（任意）

整理中に、**特定プロジェクトに依らない普遍的な作業流儀**が memory（特に feedback 系）に溜まっていることがある。これは経験知というより「規約」なので、グローバル `~/.claude/CLAUDE.md`（または当該プロジェクトの CLAUDE.md）へ昇格する候補になる。見つけたらユーザーに昇格を提案する。

振り分けの軸:
- **CLAUDE.md 向き**: 安定・チーム合意・明示的なルールで、複数プロジェクトでも確実に正しいもの（例: PR/レビュー/git の運用作法、コミットハッシュ表記）
- **memory に残す**: 創発的・経験的・文脈依存の知識、特定プロジェクトのコード/環境に紐づくもの

昇格するときは**普遍ルールだけを抽出**して CLAUDE.md に書き、元の memory ファイルは消さず「昇格済」注記＋プロジェクト固有の背景・実例を残す（二重管理を避け、CLAUDE.md=要点 / memory=背景の役割分担にする）。ツール前提・組織運用に依存するものは無理に昇格せず据え置く。

> **既に昇格済みのものを「二重管理」と誤認して消さない**。feedback ファイルに「〜へ昇格済」注記があれば、それは純粋重複でなく上記の正しい二層構造（CLAUDE.md=要点 / memory=背景）。ファイルごと削除すると背景（実例・harness 手順など CLAUDE.md に無い情報）が失われる。**MEMORY.md 索引から外す（自動ロード上の重複解消）は可、ファイル本体は残す**。削除前に必ず中身を開き、「重複」という想定と矛盾しないか確認する（想定と食い違ったら消さずユーザーに挙げる）。なお feedback のうち実態が技術知見のもの（CSS/React の挙動など）は「作業ルール」でなくナレッジなので、ナレッジ索引（または分離先 `KNOWLEDGE.md`）へ移す。

## 6. ゴミ掃除

- **空ファイル**（0 バイトの task-*.md など）を削除する。
- **壊れリンク**: 索引が指すファイルが実在するか確認し（`ls <file>`）、無いエントリを索引から削除する。
- **重複索引**: 同じファイルが複数箇所から参照され重複していたら 1 つにまとめる。
- **小ファイルの乱立（sprawl）**: 内容が薄く近接トピックのファイルが乱立していたら、関連トピックへ統合し索引を整理する。

## 7. 検証と報告

検証:
- `wc -l MEMORY.md` ＋ `wc -c MEMORY.md` で行数・容量を再測し、**行数上限とバイト/読込上限の両方**に収まったか確認する（フックの容量警告が消えたかも見る）。**上限ぎりぎりは合格ではない**——MEMORY.md は次のセッションからまた育つので、目標は上限の 5〜10% 手前。届かなければ、詳細が別所（Jira コメント・PR 本文・design-doc）に記録済みの行をもう一段圧縮する。
- `scripts/check_health.sh` を再実行すると、壊れリンク・空ファイル・**frontmatter / description 欠落**・**被参照ゼロの孤児**・**末尾セクション**の再チェックまで一括で済む。末尾セクションが「消えてよいもの」になっているかをここで必ず見る。
- 孤児として出たファイルは、①索引へ載せる ②本文から辿れるようリンクを張る ③archive へ移す ④削除、のどれかへ振り分ける。**「昇格済みだから索引から外した」ファイルは、注記に*ファイル名でリンク*して辿れるようにする**（名前を書かずに外すと、辿る道が完全に消える）。
- 進行中タスクに**完了済みが残っていない**こと、索引に**壊れリンクが無い**ことを確認する。
- 移動・要約で参照が切れていないか（task リンク・ナレッジ索引）を見る。

報告（簡潔に）:
- before → after の行数・容量
- 削除した完了タスク（と完了記録/ナレッジへの移し先）
- task へ退避した肥大エントリ
- CLAUDE.md への昇格を提案したルール（あれば）
- ゴミ掃除（空ファイル・壊れリンク・統合）の内訳
- 据え置いた・判断保留したエントリがあれば挙げる
